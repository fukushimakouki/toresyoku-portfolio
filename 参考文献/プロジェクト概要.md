## 1. プロダクト概要

ユーザーが自身の情報（体重・身長・性別・目標・アレルギーなど）と「今日の状況」を入力すると、**AIがその日の運動メニューと食事を提案する**Webアプリ。

- プロダクト名: **トレ食**（プロジェクト名 `toresyoku`）
- チーム: **4人**
- イベント: チャレキャラ（学生が半年かけてプロダクトを作り、最後にコンテストで競う育成型プログラム）
- 現状: 構想段階。実装物なし

### 誰の、どんな課題を解くのか

大学1〜2年生は「痩せたい・鍛えたい」と思っても、**何をどれだけやればいいのか分からない**。既存アプリは記録が中心で、「じゃあ今日は何をすればいいか」を教えてくれない。

### 差別化の芯

**使うほど賢くなる**こと。体重推移・過去の提案・実際にやったかどうかを次回のプロンプトに含め、その人に合った提案に寄せていく。ここが単なる「AIに聞くだけ」との違いなので、優先度を高く扱う。

### ビルドツール（Gradle）について

Javaはコードを書いただけでは動かず、毎回「ライブラリを集める → コンパイル → テスト → JARにまとめる」が必要になる。これを自動化するのがビルドツール。

**設定ファイル（`build.gradle`）をGitで共有すれば、全員のPCで同じライブラリ・同じバージョンが揃う**ので、「自分の環境では動くのに」を防げる。普段触るのは `dependencies { }` の中だけで、ライブラリを足したい時に1行追加する程度。

Maven（`pom.xml`）という選択肢もあるが、手順書がGradle前提で全員そこで環境構築済みのため **Gradle** に統一する。

### 依存関係（Spring Initializr で選ぶもの）

1. **Spring Web** — Webアプリ、Controller、API作成
2. **Thymeleaf** — HTML画面のテンプレート（★手順書に無かった。必須）
3. **MySQL Driver** — Spring BootからMySQLへ接続
4. **Validation** — ユーザー入力値のチェック
5. **Spring Boot DevTools** — 開発中の自動再起動

Spring Data JPA は**選ばない**。代わりに MyBatis を使うが、これはSpringの公式スターターではなくコミュニティ製のため、`build.gradle` に手で追加する。

```gradle
dependencies {
    implementation 'org.mybatis.spring.boot:mybatis-spring-boot-starter:<Boot4対応版>'
    // 他の依存はInitializrが自動で書いてくれる
}
```

> ⚠️ **要確認（優先度: 高）**
> `mybatis-spring-boot-starter` は Spring Boot のバージョンに追従する形でリリースされている。**Spring Boot 4.1.1 に対応した版が出ているかを Maven Central で確認**すること。
> - 対応版がある → そのバージョンを指定して進める
> - 対応版が無い／起動時にエラーになる → **Spring Boot を 3.5系に落とす**（MyBatisは3.0系スターターで安定して動く）
>
> 土曜デモはDBを使わないため**この確認はデモ開始をブロックしない**が、本番フェーズに入る前に必ず決着させる。

### ディレクトリ構成

```
src/main/java/com/example/toresyoku/
  ├─ controller     # 画面・リクエストの受け口
  ├─ service        # 業務ロジック（GeminiService など）
  ├─ mapper         # MyBatisのSQLインターフェース（旧: repository）
  ├─ entity         # DBのテーブルに対応するクラス
  ├─ dto            # 画面やAPIとやり取りする入れ物
  └─ exception      # エラー処理
src/main/resources/
  ├─ templates/     # Thymeleafのhtml
  ├─ mapper/        # MyBatisのXML（SQL）
  └─ application.properties
```

> 手順書の `repository` は Spring Data JPA の用語なので、MyBatis に合わせて **`mapper`** に読み替える。

### APIキーの管理

`application.properties` に以下を書き、**キー本体は環境変数から読む**。

```properties
gemini.api.key=${GEMINI_API_KEY}
```

**コードへの直書き・Gitへのコミットは禁止。** キーは発行済みなので、チーム内で安全な経路（コミット以外）で共有する。

## 7. サーバ側機能一覧

### デモ用（土曜の最小構成）

- **入力受付**: プロフィール＋今日の状況をフォームから受け取りバリデーション
- **プロンプト生成**: 入力値をテンプレートに埋め込んでGemini向け指示文を組み立て
- **AI呼び出し**: Gemini APIへリクエスト。タイムアウト・エラー処理
- **結果パース**: JSON → Java DTO
- **画面受け渡し**: DTOをThymeleafに渡す

### 本番用（12月に向けて追加）

- 認証・認可: ユーザー登録、ログイン、自分のデータのみ閲覧可（Spring Security）
- プロフィール管理: CRUD
- 体重記録: 日付ごとの記録・更新・期間指定取得
- BMI・基礎代謝・目標カロリー計算（プロンプトにも渡す）
- 提案履歴の保存と過去分閲覧
- 食事・運動の実施記録: 提案どおりやったかのチェック、達成率集計
- **提案の文脈強化**: 体重推移・過去提案・実施状況をプロンプトに含める（**優先度高**。差別化ポイント）
- 目標管理: 目標体重・期限・進捗率
- API利用制御: 1日あたり回数制限、レート制限
- キャッシュ: 同日同入力なら保存済みを返す
- ログ・エラー処理: 失敗記録、リトライ、フォールバック固定メニュー
- 外部連携（余裕があれば）: 食品カロリーDB、通知

### 想定テーブル（本番用）

`user` / `profile` / `weight_log` / `suggestion` / `meal_log` / `training_log`

## 8. 土曜デモの実装計画

**DB・ログイン・Security・MyBatisは全て使わない。** Gemini呼び出しから画面表示までの一本道だけを通す。

```
src/main/java/com/example/toresyoku/
  ├─ controller/DemoController.java      # GET /（入力フォーム）, POST /suggest（結果表示）
  ├─ service/GeminiService.java          # Gemini APIを呼び、JSONを受け取る
  └─ dto/SuggestionResponse.java 等
src/main/resources/templates/
  ├─ index.html    # 体重・身長・性別・目標・今日の状況のフォーム
  └─ result.html   # 運動3つ・食事3食・コメントを表示
application.properties                    # gemini.api.key=${GEMINI_API_KEY}
```

実装順: **GeminiService → Controller → 画面**（AI呼び出しが通ることを最初に確かめる）

CampusTradeの資産は、プロジェクトごとコピーせず **`.java` と `.html` を必要な分だけコピペ**して流用する（Spring Bootのバージョンが違うため）。

### デモ演出

- 「今日の状況」欄に**発表中にその場で打ち込み**、提案が変わるのを見せる
- フォームに発表用プロフィールを初期値で入れておく
- **API失敗に備え、事前生成した結果のスクショをスライドに必ず入れる**

**木曜（9/3）夜まで**に「フォーム送信 → Geminiの結果が画面に出る」まで到達しなければ、金曜は**スクショ版に切り替えてリハに集中**する。
